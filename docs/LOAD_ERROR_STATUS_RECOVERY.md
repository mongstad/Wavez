# Successful-open error recovery

A successful `.wvz` open clears the active diagnostic belonging to a previous
failed open: the failed-open banner, its stored details, and the bottom status
failure notice/error icon. This happens without an acknowledgement action.

An initial-sample decode failure can also appear on the Scene controller. The
status adapter retains that exact diagnostic only under **Open file**, rather
than adding a second **Scene** notice. The existing successful-open cleanup then
clears it. Readiness can still say **Unavailable** while the failed sample is
current; the actual reader error remains available through the banner's Details
and **File → Details…** before recovery.

Picker cancellation, failed retries and unrelated information do not clear the
current open failure. Independent Scene, particle, field, mesh and Jobs
notices retain their existing ownership and acknowledgement behavior. Therefore
**Ready • Failed — details** can still be correct after a successful load if
another retained failure exists. Its details identify that other owner.
Session logs retain the earlier failed attempt and subsequent successful open.

The loader, scientific data, camera framing, playback/preparation, cache policy,
legends and job execution are unchanged. Build 75 proposes this status correction
for issue #295 and remains pending owner review.

## Known loader limitation

A failed header/metadata admission preserves the prior usable reader, layers,
committed sample, camera and presentation. However, accepted main already installs
a newly admitted reader before decoding its initial sample. A payload-level
initial-sample failure (such as duplicate particle IDs) can therefore replace the
prior scene with an unavailable scene. That late-failure rollback is **not fixed**
by this presentation-only change. It was reproduced on accepted `61c38dd`; see
[the baseline and focused evidence](evidence/issue-295/README.md). Do not interpret
the status fix as transactional recovery for every failure stage.

## Owner checks

1. At normal and compact sizes, open a valid WVZ, seek, then attempt an invalid or
   unsupported file. Confirm the prior sample remains usable, the bottom status
   has an error icon and Failed notice, and both Details routes explain it.
2. Cancel the picker, or make another failing attempt: the current failure stays
   available. Open another valid WVZ: the banner and Open file diagnostic disappear,
   and **File → Details…** has no stale failure or acknowledgement action when
   no other failure exists.
3. For the reproduced initial-sample case, start a fresh viewer and open
   `duplicate.wvz` generated by the validation command below. Inspect the duplicate
   ID diagnostic; then open its `scene.wvz`. Confirm Ready, the check icon, and
   cleared failure details. Repeat the failure/success cycle.
4. With an independent retained job failure, open a valid WVZ. That job's Failed
   notice/details should remain, while Open file no longer appears. Review your
   normal playback/cache/legend presentation in Forward+ and Compatibility.

Run focused native validation with an external Godot executable:

```sh
python tools/validate_load_error_recovery.py \
  --godot /absolute/path/to/godot \
  --renderer forward_plus --output-dir /tmp/wavez-load-forward
python tools/validate_load_error_recovery.py \
  --godot /absolute/path/to/godot \
  --renderer gl_compatibility --output-dir /tmp/wavez-load-compatibility
```

The output directory must not already exist. Fixtures and isolated application
user data stay there; no input-device helper is used. The regression uses the
production open/status paths, disables preparation workers for its tiny fixture,
and injects published job state to check that UI cleanup does not change Jobs.
It does not run real export/analysis workers or the unrelated full suite.
