# Compatibility scalar sampling and readback: measured results

Issue [#354](https://github.com/mongstad/Wavez/issues/354), executed 2026-10-11.
**The tested RF shader sampling preserves negative and above-one values in
Compatibility. Its raw texture readback does not.** Forward+ and Compatibility
produce identical encoded scalar results through both isolated Godot and Wavez
upload paths. A separate finding remains: hardware linear filtering **FAILS** the
predeclared 0.0002 ideal-interpolation tolerance at 13/16 off-grid probes in both
renderers. Explicit eight-texel shader interpolation passes that same tolerance.
No application behavior is changed or general GPU precision certification claimed.

## Fixture and independent scalar oracle

The float64 grid has shape `(nz,ny,nx)=(2,3,8)` and values
`[-0.5,-0.125,0,0.5,1,1.2,1.8,2.4][x] + 0.125*y + 0.25*z`.
Origin **(-0.75,0.25,-0.5) m**, spacing **(0.25,0.5,0.125) m**, node centering,
identity affine, dimensionless scalar, native time **0.125 s**. Forty-eight exact
texel centers cover six negative, 19 normalized and 23 above-one values, spanning
**-0.5 to 2.9**. Sixteen additional interior grid coordinates use RNG seed 354;
their actual expected values are positive. Full coordinates and values are in
`run-01/oracle.json`.

**PASS:** source/WVZ1 float64 arrays, dtype and time are exact. Python source probes
agree with an independent NumPy trilinear calculation within **4.441e-16**.
Native original source hashes and CPU-prepared RF float32 planes agree exactly
with independently generated bytes. Maximum f64→f32 rounding is **9.536743173e-8**
(limit **1.2e-7**); native world-space source-probe error is **2.319146790e-7**
(limit **2e-6**). There is no LOD, mipmapping or temporal interpolation.

The Wavez path uses the real native reader, `field_prepare` and `GridView` upload.
The standalone Godot project builds the same RF planes arithmetically and loads
no Wavez code. Both sample the same known coordinates with an external shader.
The numeric oracle is independent of raw `ImageTexture3D.get_data()`.

## Observable shader mapping and results

For each sampled scalar v, the shader encodes `round((v+2)/8 * 65535)` into
separate high/low RG bytes; blue=255 checks framing. All tested values are inside
the encoder's [-2,6] range. The 512×16 non-HDR 2D framebuffer has 64 tiles, read
at their centers. CPU decoding recovers v to a step of **8/65535**, with at most
**6.104e-5** half-step error. This framebuffer contains deliberately encoded byte
channels, not a raw RF readback. Uniform-value calibration bypasses the texture
and validates the observable path. Declared scalar tolerance: **0.0002**.

## Why raw readback is unreliable here

At the exact tested Godot revision,
[`texture_3d_get` and its helper](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/drivers/gles3/storage/texture_storage.cpp#L1710)
read through an unsigned-byte RGBA framebuffer and then convert the returned
Image back to the requested format. Conversion back to RF cannot restore clipped
values or lost byte precision. Measured Compatibility raw error reaches
**1.9000000954**; Forward+ returns the original float32 values exactly after JSON
numbers are re-encoded as f32.

The helper also uses layer/depth coordinates rather than texel-center layer
coordinates. In this two-layer fixture, raw layer 1 blends the two source layers:
at grid **(2,0,1)**, source **0.25** and encoded shader **0.2500343328** become
raw **0.1254902035**. The clipped half-layer model agrees within **0.0019607842**
byte quantization. This is a readback location/format limitation; actual shader
samples preserve the declared coordinates and values within the tested bounds.
The upstream RF path also has a capability-dependent RH fallback; other devices
and physical storage formats were not independently queried or certified.

## Production slice, volume and range controls

Unmodified production `GridView`, `slice.gdshader` and `volume.gdshader` render
eight constant float64 2×2×2 fields. Their values are the eight base values above,
at native times i/8, node box [-0.5,0.5]×[-0.5,0.5]×[-0.25,0.25] m. Camera
(0,0,2), target zero, orthographic height 2 m, near/far 0.01/10 m; 128×128 native
viewport, center pixel (64,64), black background, gray LUT, linear tone mapping,
no glow/fog/opaque occlusion. Known volume ray length **0.5 m**, opacity **2/m**,
step **0.01 m**. These are production components in a controlled scene, not a
full application UI, packaged or nonconstant-volume certification.

Predeclared RGB limits are **0.012 slice / 0.02 volume**, with minimum above-one
separation **0.04**; actual minimum separation is **0.0941176414**. Each production
process completes **57 checks, zero failures**, clean log and exit 0. The independent
assessment passes all **80** production value/guard cases and **six** separation
checks. The measured Compatibility low-value slice deviation remains explicit;
passing these bounds does not establish pixel identity or exact color fidelity.

CPU predictions use scalar normalization and analytic extinction
`alpha=1-exp(-2*weight*0.5)`. Forward+ output is modeled as
`srgb(srgb_to_linear(gray)*alpha)`; Compatibility as `gray*alpha`. Their different
color/compositing pipelines are tested separately, not mistaken for scalar loss.
Signed opacity maps weight over [-1,3]; positive opacity maps it over [0,1]. The
latter intentionally hides negative/zero values. A narrow color range intentionally
maps all values above 1 to white even though texture sampling still distinguishes
them. Correct probes therefore do not guarantee an informative choice of visuals.

## Impact, proposed follow-up and remaining limits

The original [0,1] uncertainty is resolved for these RF paths: **clipping is in
Compatibility raw readback, not the tested sampled scalar values**. Hardware
filtering precision remains a distinct observed failure in both renderers. A
~0.0012 scalar difference can be amplified by a narrow color or opacity range,
while float64 probes stay accurate and a wide-range screenshot appears acceptable.

Proposed **separate, owner-scoped work**: evaluate explicit eight-fetch trilinear
sampling in both scientific field shaders, including performance, LOD, boundary,
colormap and opacity tests before choosing a behavior change. Independently,
float-preserving readback and texel-center layer addressing could correct the
engine diagnostic. Neither proposal is implemented here; scientific data are not
normalized, clamped or silently corrected. Exact filter-error mechanism remains
**NOT VERIFIED**, including the failed simple 8-bit-weight hypothesis.

Retained attempts: a nonbinary-coordinate initial fixture exposed 16 unavailable
upper-Y boundary source probes and failed before shader testing. Binary-exact
coordinates isolate this scalar experiment; general boundary-coordinate robustness
is not claimed fixed. The initial native run lacked an oracle and ended by watchdog.
An initial dual-sampler control had conflicting filter state; final passes use
one sampler. An overly strict production probe equality was corrected to the
already-declared numerical bound. All attempts remain external; thresholds and
scientific source arrays in the final controlled fixture were not changed to pass.

**NOT RUN/NOT VERIFIED:** other GPUs/drivers/OSes, Mobile, RH fallback, other texture
formats, values outside [-0.5,2.9], subnormals/NaN/Inf, negative off-grid precision,
mipmaps/LOD, affine or large-coordinate stress, nonconstant ray integration,
occlusion/translucent mixtures, other colormaps, packages, monitor calibration,
long sessions, video, Selection/Analysis or general-purpose GPU precision.
